🏗️ System Architecture (Two-Stage Pipeline)

CineCrave decouples fast nearest-neighbor retrieval from compute-intensive ranking and diversity constraints to maintain sub-15ms response latency over thousands of items.

1
Embedding Ingestion
Aggregates movie title, overview, genres, cast, director, and keywords into dense 384-dimensional embeddings via Sentence-BERT (all-MiniLM-L6-v2).
2
FAISS Candidate Retrieval
Fast sub-millisecond retrieval of the top k=50 nearest neighbor items using IndexFlatIP on L2-normalized vectors (exact Cosine Similarity).
3
Hybrid Re-Ranking
Combines semantic similarity (0.85), TMDB log-popularity (0.10), and novelty reward (0.05) to balance mainstream appeal with niche discoveries.
4
MMR Decision Layer
Applies Maximal Marginal Relevance (MMR) with λ = 0.7 to penalize redundancy and prevent franchise/sequel flooding.
🔬 Core Algorithms & Mathematical Formulations

1. Hybrid Ranking Score

Balances relevance with popularity bias and novelty to surface both crowd-favorites and hidden gems:

Score(d) = w_sim · Sim(d) + w_pop · Pop(d) + w_nov · Nov(d)

Where Nov(d) = 1 / (log(1 + Pop(d)) + 1.0) provides an inverse logarithmic popularity reward.

2. Maximal Marginal Relevance (MMR)

Greedily selects the next item that maximizes relevance while minimizing similarity to already selected items:

MMR(d) = λ · Score(d, Q) - (1 - λ) · max_{s ∈ S} CosSim(d, s)

λ = 0.7 prevents 5 Batman movies from occupying all top 5 slots when querying The Dark Knight.

💡 System Design Insights & FAQs

Architectural decisions, latency tradeoffs, and scaling considerations for production recommendation engines:

1. Why use a two-stage Retrieve-and-Rank design instead of ranking all items directly? ▼
Full catalog re-ranking is O(N). For 50k+ items, calculating multi-feature scores and running MMR takes over 200ms. By using FAISS (approximate nearest neighbors in O(log N)) for candidate generation, we prune the catalog down to 50 candidates in <1ms, allowing deep ranking and MMR diversity to execute in <15ms total latency.
2. How did you prevent popular blockbuster movies from drowning out niche recommendations? ▼
We applied two mechanisms: 1) Logarithmic scaling: log(1 + popularity) to compress extreme blockbuster outliers (e.g. Minions with popularity 875 vs median of 20), and 2) Novelty weighting: an explicit feature inversely proportional to log popularity that boosts high-quality hidden gems.
3. What is the filter bubble problem, and how does your MMR implementation solve it? ▼
Without MMR, searching The Dark Knight returns 5 Batman sequels. MMR uses greedy iterative selection where each candidate is scored by λ · Relevance - (1-λ) · Max_Similarity(Selected). This actively penalizes pairwise embedding similarity with already selected movies, guaranteeing thematic diversity (e.g. recommending Watchmen and Pulp Fiction instead of pure sequels).
4. How would you scale this system to 10 Million users in production? ▼
1) Upgrade FAISS from IndexFlatIP to IndexIVFFlat or HNSW on GPU clusters for sub-millisecond retrieval at scale.
2) Implement a Redis caching layer for top item recommendations with TTLs.
3) Update user vector embeddings asynchronously via Kafka / Celery background workers upon new watch events.
